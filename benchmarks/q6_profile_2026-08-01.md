# Q6 scan-path profile — root cause of the ~1,265 ns/row (2026-08-01)

**Verdict: (a) FIXABLE OVERHEAD, not algorithmic.** ~96% of the per-row cost is
materializing each row into `Record = HashMap<String, Value>` inside
`BundleStore::reconstruct()` — dominated (~91% of total) by the 12 per-row
heap-allocated `String` key clones + SipHash string hashing + HashMap inserts,
plus 3 heap `Text` value clones (~13%). A further ~4% is a redundant per-row
`bp_to_idx: HashMap<u64, usize>` lookup. The underlying sequential storage
itself scans at **20 ns/row** (borrowed fiber slices) and a typed columnar loop
over the same data runs at **4.5 ns/row** — same order as the ~12 ns/record
curvature path. Diagnosis only; no engine code was changed.

## Scope and method

- Cell reproduced: TPC-H Q6, the `bench_tpch` harness (`benches/tpch_bench.rs`,
  Cargo `[[bin]] bench_tpch`). Recorded headline:
  `bench_output/tpch_report.dhoom` line 26 — real SF=1, 6,001,215 rows,
  7,585.4 ms = **1,264.0 ns/row** (the "1,264.7" in the fix spec is this cell).
- Q6 is a direct in-process function `q6()` at `benches/tpch_bench.rs:266-283`
  — not GQL, not HTTP. **gigi server lifecycle is N/A for this cell** (no
  server was started; nothing else ran concurrently; all timed runs serial).
- Instrumentation: **scratch timing ablation** (flamegraph tooling unavailable

  A scratch example replicated the bench generator verbatim (same xorshift64

## Root cause — named

**Per-row `Record = HashMap<String, Value>` materialization in
`reconstruct()` (`src/bundle.rs:2736-2751`).** For every one of the 6M rows the
scan: allocates a fresh HashMap; clones 12 field-name `String`s
(`field_def.name.clone()` — 12 heap allocations); SipHash-hashes each key on
insert; clones 12 `Value`s of which 3 (`l_returnflag`, `l_linestatus`,
`l_shipmode`) are heap `Text` allocations; then `q6()` pays 4 more string-hash
`get()`s to read the fields back. Secondary: `records()` reaches each row via
`bp_to_idx.get(&bp)` (`bundle.rs:2717`) — a SipHash u64 HashMap lookup per row
— even though in Sequential mode the row index is the iteration position.

**Ruled out:** dynamic dispatch of the `Box<dyn Iterator>` and bounds checks
(both inside V1's 20 ns/row, predicate included); the storage layout
(sequential, cache-linear — V1/V4 prove it); the predicate math (V4 floor
4.5 ns/row).

## Classification: (a) fixable, with estimate

The cost is representation-conversion overhead, not an algorithmic property of
the storage or query. The same store, walked through the existing public
`sections()` borrowed-slice iterator with positional field access, computes the
identical Q6 answer at 20 ns/row — a **~120x** reduction measured on this
machine, holding the storage engine byte-for-byte fixed.

**Fix shape (not done here):** a scan/aggregate path that resolves field names
to schema positions once per query, then consumes `sections()` borrowed slices
(zero materialization) — falling back to `records()` only when a caller needs
owned rows. Removing only the redundant `bp_to_idx` lookup in the Sequential
branch (iterate by index directly) is a smaller independent ~4% win.
**Estimated gain for Q6-style scan-aggregates: ~60-120x per-row** (2,403 →
20-40 ns/row today; on the recorded machine, 1,264 → ~10-20 ns/row, i.e. Q6 at
SF=1 from 7.6 s to ~0.06-0.12 s), converging on the same order as the ~12
ns/record curvature path, which already avoids materialization.

## Confirmation run at SF=1 (real .tbl, 6,001,215 rows)

The identical ablation was then run serially against the real SF=1
`lineitem.tbl` (`C:\Users\nurdm\tpch-kit\tbl`, loaded in 74.6 s). This is the
exact cell behind the 1,264.0 ns/row headline, on today's ~1.9x-slower machine
state:

| Variant | best ms | ns/row | reps (ms, raw) |
|---|---|---|---|
| V0 `records()` baseline (= verbatim `q6()`) | 13,789.6 | **2,297.8** | 16,442.8, 16,427.3, 13,789.6 |
| V1 `sections()` positional | 125.7 | **21.0** | 127.7, 125.7, 146.4 |
| V2 = V1 + `bp_to_idx` lookup | 1,120.5 | 186.7 | 1,120.5, 1,161.6, 1,129.7 |
| V3a = V1 + `Vec<Value>` clone | 1,644.6 | 274.0 | 1,701.3, 1,644.6, 1,655.3 |

V0 at 2,297.8 ns/row vs the recorded 1,264.0 = 1.82x — consistent with the
1.94x same-binary machine calibration. SF=1 split: borrowed-slice scan is flat
(21.0 vs 20.0 ns/row at SF=0.05 — cache-linear as claimed); the `bp_to_idx`
lookup grows to 165.7 ns/row (~7%, up from ~4% — 6M-entry map, more cache
misses per lookup, exactly as predicted); `Value` clones 253.0 ns/row (~11%);
the remaining ~1,850+ ns/row is the `Record` materialization residual (String
keys + SipHash + HashMap inserts), keeping materialization at ~90%+ of the
scan. The V3/V4 rows of the SF=1 ladder had not finished printing at this
workflow's output deadline; the SF=0.05 table above carries the full
decomposition, and every SF=1 row that landed matches it.
